# AgentCouncil

A multi-agent "council" app built on the **Microsoft Agent Framework** (.NET, 1.27) and **.NET Aspire**. A user invites any of five debaters (**Moderator, Optimistic, Skeptic, Pragmatic, Pessimistic**), drops a topic, and they debate it via a per-session choice of **handoff**, **group chat (round-robin)** or **Magentic One** orchestration, then return the floor to the user. Each agent opens by reacting to the previous speaker by name, so it reads like a conversation. On request, **Pragmatic acts**: a standalone *harness* agent plans todos, writes files to a shared workspace behind an **approval gate**, loops until its todo list is empty and can dispatch a background **Researcher**. Backed by the **Azure OpenAI Responses API** (v1 endpoint, API-key auth), so debaters can **search the web** and stream **reasoning summaries** into a per-message side log. Visualized through the Agent Framework **DevUI** debugger and a custom **Blazor** front-end.

## Architecture

```
src/AgentCouncil.AppHost          Aspire orchestration: openai connection + agents + web
src/AgentCouncil.ServiceDefaults  Shared telemetry/health/service-discovery (AddServiceDefaults / MapDefaultEndpoints)
src/AgentCouncil.Agents           ASP.NET Core: debaters, harness agent, workflows, DevUI, SignalR hub
src/AgentCouncil.Web              Blazor Server: council UI
test/AgentCouncil.AppHost.Tests   AppHost model test
```

### AgentCouncil.Agents
- **`AzureOpenAIChatClient.cs`** — `AddCouncilChatClient()` parses the single `openai` connection string (`Endpoint=...;Key=...;Deployment=...[;CheapDeployment=...]`) and registers two Responses-API `IChatClient`s (`OpenAIClient` on `<endpoint>/openai/v1/`) with OpenTelemetry (source `AgentCouncil.Agents`): the default one (Moderator + harness) and a keyed `"cheap"` one (personas, Researcher, compaction summaries). Without `CheapDeployment` both use `Deployment`. A `Stateless` middleware sets `store=false` and strips reasoning/web-search items from the input (see gotchas).
- **`Agents/CouncilAgents.cs`** — singleton holding every agent:
  - `CreateDebater(AgentSetup, seated, canHandOff)` builds one debater from `(Name, MaxOutputTokens, Effort)`. Every debater gets the shared `Conversation` rule (react to the previous speaker by name, no lists), a cast line naming only who is `seated`, and in handoff mode a rule to end each turn with a handoff call. The budget is applied twice — as `ChatOptions.MaxOutputTokens` and as a turn-length rule in the instructions (`AgentSetup.Style`: one sentence / two / four-with-an-example) — and `Effort` becomes `ChatOptions.Reasoning` (with a reasoning summary for the side log) unless it is `"auto"` (which sends nothing, the only safe default on a non-reasoning deployment). The session manager builds a fresh set per line-up; agents hold no state, so this is free.
  - The five debaters (default-tuned singletons, for DevUI and the graph endpoint). Every one has `OrphanToolContentFilter` first (see gotchas), then a `CompactionProvider` (summarization past 6000 tokens). The **Skeptic** also gets a read-only `FileAccessProvider` over the workspace and an `AgentSkillsProvider` over `skills/` (SKILL.md files, e.g. `skills/devils-advocate`). **Pragmatic** gets a `FileAccessProvider` whose writes need approval, so it can write a file mid-debate when asked; the approval surfaces from the workflow.
  - `CreateMagenticManager(seated)` — the Moderator as the Magentic manager: no token cap (it writes JSON ledgers) and no tools.
  - **`Harness`** — Pragmatic "with hands": `LoopAgent(ToolApprovalAgent(ChatClientAgent))`. Its providers are `FileAccessProvider` (reads free, writes need approval), `TodoProvider`, `AgentModeProvider` (`plan`/`execute`) and `BackgroundAgentsProvider` (Researcher). Its compaction sits on the chat client (`UseAIContextProviders` on a `ChatClientBuilder`), not on the agent (see gotchas). The loop (`TodoCompletionLoopEvaluator`, execute mode only, max 12 iterations) keeps going until the todos are done and stops whenever an approval is pending.
  - The workspace is `FileSystemAgentFileStore` over `<content root>/workspace` (git-ignored), **shared by all connections**.
- **`Workflow/CouncilWorkflow.cs`** — builds the workflows per session for the invited line-up. `BuildHandoff(moderator, personas)`: a full mesh (Moderator → every persona; every persona → the Moderator and every other persona), `EnableReturnToPrevious()`, `WithToolCallFilteringBehavior(All)`. Nothing caps persona-to-persona passing; the instructions steer it back to the Moderator. `BuildGroupChat(members, rounds)`: `RoundRobinGroupChatManager` with `MaximumIterationCount = rounds * members.Count`. `BuildMagentic(manager, personas, rounds)`: `CreateMagenticBuilderWith`, `WithMaxRounds(rounds * personas.Count)`, no plan sign-off.
- **`Agents/OrphanToolContentFilter.cs`** — an `AIContextProvider` that, before a debater's (or the Magentic manager's) turn, turns other members' replies into `[Name] text` user lines and drops other agents' approval exchanges and any approval or tool content missing its other half.
- **`Hubs/CouncilHub.cs`** + **`CouncilSessionManager.cs`** — SignalR hub at `/councilhub`. One `CouncilSession` per connection. Handoff and group chat keep one persistent `StreamingRun`; Magentic opens a fresh run per user turn (`StartMagenticTurnAsync`), seeded with a `List<ChatMessage>` history that the hub builds from what it streams. The session also keeps the harness agent's own `AgentSession`, the debate text the harness hasn't seen, the pending harness approval, a queue of pending **workflow** approvals, and the tools the user picked *Always approve* for.
  - `DriveAsync` watches the run with `WatchStreamAsync(blockOnPendingRequest: false)`. A `RequestInfoEvent` carrying a `ToolApprovalRequestContent` goes to the client as `ApprovalRequested` (or is answered at once when the tool is always-approved). `RespondToApproval` answers it with `SendResponseAsync` and resumes the run. Magentic progress-ledger instructions are shown as Moderator lines, and the manager's final answer (in the `WorkflowOutputEvent`) as the Moderator's verdict.
  - Server methods: `StartCouncil(topic, mode, roundsPerAgent, AgentSetup[] lineup)` (`mode` = `"handoff"` | `"groupchat"` | `"magentic"`; handoff and Magentic always seat the Moderator; at least one persona and two agents), `SendUserInput(text)`, `AskPragmatic(instruction)`, `RespondToApproval(decision)` (`"approve"` | `"always"` | `"deny"`; goes to the workflow or the harness, whichever is waiting), `ReadWorkspaceFile(path)`, `DeleteWorkspaceFile(path)`.
  - Client-bound: `AgentDelta(agent, text)`, `AgentLog(agent, kind, text)` (`reasoning` streamed in chunks, `tool`, `result`, `search`; handoff calls hidden), `AwaitUserInput()`, `CouncilError(message)`, `ApprovalRequested(agent, tool, argsJson)`, `HarnessState(mode, TodoView[] todos, researching)`, `FilesChanged(paths[])`.
  - Debater turn length comes from each agent's token budget, not a fixed rule (default 400 ≈ 2 sentences).
  - `EndAsync` calls `BackgroundAgentsProvider.ReleaseSessionAsync` so Researcher tasks stop when the tab closes.
- **`Program.cs`** — registers everything. **Development-only**: DevUI (`AddDevUI` + `MapOpenAIResponses`/`MapOpenAIConversations`/`MapDevUI`) and `GET /council/graph`, which returns the full-roster handoff graph as Mermaid (`WorkflowVisualizer`).

### AgentCouncil.Web
- **`Services/CouncilClient.cs`** — per-circuit `HubConnection` to the `agents` service. Resolves the hub URL from Aspire service-discovery config (`services:agents:https:0`, falling back to `http`).
- **`Components/Pages/Council.razor`** — two animated start stages. (1) *Who do you want to talk with?*: a roster row above an **always-on round table**. Each character (🛡️ Moderator, ☀️ Optimistic, 🧐 Skeptic, 🔨 Pragmatic, 🌧️ Pessimistic) is one absolutely-positioned token whose `--x`/`--y` come from `Spot()`: the uninvited queue in the top row, the invited sit on the table's far arc (widening from ±35° to ±105° as it fills), and the user's crown holds the near side. Only the transform changes, so inviting someone walks them down into a seat and re-spaces everyone else; the table rides a `--lift` that closes the gap once the roster empties. A conic-gradient ring around each head is that agent's token budget. Below the table, one **tuning row** per invited agent: a native range slider (150–1500 output tokens, with the turn shape it implies) and `auto/⚡/⚡⚡/⚡⚡⚡` effort chips, both sent to the hub as `AgentSetup[]`. (2) The chosen party → mode picker (handoff / group chat / Magentic One + turns-per-agent) → optional **Resume from** picker over the workspace `.md` files (the hub pushes `FilesChanged` on connect; the chosen record is read and prepended to the opening message, topic becomes optional) → topic box; handoff and Magentic auto-seat the Moderator.
  - Session **stage rail**: seats for the invited agents only, with a glowing "floor token" on the current speaker (derived client-side from `AgentDelta` speaker changes). Below it: mode chips (orchestration, Pragmatic `plan`/`execute`, researching count), Pragmatic's **todo panel** and the **workspace** file list (click to preview, rendered as markdown).
  - Header: **⟲ New session** disposes the hub connection (ending the server session) and reloads.
  - Transcript: emoji avatar, colored name and role chip per message, and a collapsible **reasoning & tools** log to the right of each bubble; bodies render **markdown via Markdig** (`DisableHtml` — model output is never injected as raw HTML).
  - Reply box: **Send** (continue the debate) and **🔨 Pragmatic, act** (run the harness). In plan mode with open todos a **Confirm plan** bar appears. An **approval modal** offers Approve / Always approve / Deny, for both harness writes and writes raised inside the debate workflow.
  - Agent identity (title, icon, role, blurb, catchphrase, color) lives in the `Members` dictionary in this file; `Name` is the hub key.

## How to run

1. Store the Azure OpenAI connection string in **AppHost user-secrets** (one combined string carries endpoint, key, deployment, and an optional cheaper deployment for the personas):
   ```bash
   dotnet user-secrets --project src/AgentCouncil.AppHost set "ConnectionStrings:openai" "Endpoint=https://<resource>.openai.azure.com/;Key=<key>;Deployment=<deployment>;CheapDeployment=<optional-deployment>"
   ```
2. Run the app host:
   ```bash
   dotnet run --project src/AgentCouncil.AppHost
   ```
3. Open the **Aspire dashboard** (URL printed on startup) and confirm `agents` + `web` are healthy.
4. **DevUI**: open `https://localhost:<agents-port>/devui` → the five debaters appear; send a topic and watch turns + traces.
5. **Blazor**: open the `web` endpoint → invite agents → drop a topic (e.g. *"Should we adopt a 4-day work week?"*) → debate → press **🔨 Pragmatic, act**. It proposes todos in plan mode; confirm and it switches to execute. Approve its first write, pick *Always approve* for the next, and watch `decision-record.md` appear in the workspace pane. Then ask the Skeptic to rebut the record (it greps the file).
6. Agent/LLM OpenTelemetry traces, including the token split by model, show up in the Aspire dashboard.

## Conventions / gotchas
- **Central package management**: all versions live in `Directory.Packages.props`; project files use versionless `<PackageReference>`. Agent Framework Hosting/DevUI are **prerelease** (`*-preview`); core + Workflows are GA. The harness types are `[Experimental]` (`MAAI001`, suppressed in the Agents csproj).
- **Tool approvals round-trip through workflows since 1.27** (they didn't in 1.19). An approval-gated tool on a workflow agent surfaces as a `RequestInfoEvent` carrying `ToolApprovalRequestContent`; answer it with `run.SendResponseAsync(request.CreateResponse(approval.CreateResponse(true)))`. Verified for handoff and group chat; the Magentic docs say participants support it too. *Always approve* inside a workflow is the hub's own `AlwaysApprovedTools` set, because no `ToolApprovalAgent` sits in the workflow.
- **After an approved call in a handoff, the next agent fails** unless `OrphanToolContentFilter` runs first. The shared conversation gives it the caller's approval request and response. Approval binding (1.22+) only honours responses to requests that the agent itself surfaced, so it drops the response, and `FunctionInvokingChatClient` throws *"ToolApprovalRequestContent found with FunctionCall.CallId(s) … that have no matching ToolApprovalResponseContent"*. With the default tool-call filtering, Azure OpenAI instead rejects an orphan `tool` message. Keep the filter first in every debater's providers.
- **Don't put `CompactionProvider` on the harness agent** (`AIContextProviders`). Together with `TodoProvider` it still breaks `ToolApprovalAgent` in 1.27, even before it summarizes anything: the approved call never runs and the model replays its last tool calls (seen: 82 `file_access_write` calls, 0 files). On the chat client (`chatClient.AsBuilder().UseAIContextProviders(compaction)`) it compacts per service call and approvals work; verified with forced summarization.
- **Group chat runs on one persistent `StreamingRun` since 1.27.** In 1.19 a second run started with no history, hence the old per-turn reseed. Send each user turn as a `List<ChatMessage>` followed by a `TurnToken`.
- **A Magentic workflow runs exactly one task.** A second message on the same run fails with *"This Magentic orchestration has already terminated"*, so each user turn builds a new workflow seeded with the history.
- **Responses API is used stateless.** With the default `store=true` a response id comes back and `ChatClientAgent` switches to `previous_response_id`, which breaks the workflows' shared history. With `store=false`, replayed reasoning/web-search items have no stored id and are rejected, so `Stateless` strips them; and the API has no author name on input messages, hence the `[Name]` tagging in `OrphanToolContentFilter`. Web search on Azure needs a GPT-4.1+ deployment and may need enabling per resource.
- **DevUI pipeline order matters**: `MapOpenAIResponses()` → `MapOpenAIConversations()` → `MapDevUI()`, and it's guarded by `IsDevelopment()`.
- **Handoff and group chat state** is held by the per-connection `StreamingRun` (opened once via `InProcessExecution.OpenStreamingAsync`), not by a manually-managed message list. A turn ends when `WatchStreamAsync` completes with no further handoff and no pending request — that's the "ask the user" moment.
- **Don't raise `HubOptions.MaximumParallelInvocationsPerClient`** (default 1): per-connection invocations are serialized, which is the only turn lock the hub has. It is also why an approval answer arrives as a *new* hub call (resuming the workflow run, or starting a new harness run), never awaited inside a streaming one.
- The **AppHost must not** carry a plain `<ProjectReference>` to `ServiceDefaults` (triggers `ASPIRE004`); only `agents` and `web` are referenced as resources.
